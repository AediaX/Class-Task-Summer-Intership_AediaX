Part 01

QA Fundamentals — The Vocabulary You're Judged On

Before automation, an interviewer wants to know you understand testing as a discipline. Get these definitions solid — half the "easy" marks in a technical round come from precise vocabulary, not clever answers.

What is Quality Assurance vs Quality Control vs Testing

  • Quality Assurance (QA): Process-oriented. It's about preventing defects by improving how the software is built — reviews, standards, process audits.
  • Quality Control (QC): Product-oriented. It's about finding defects in the actual product that was built.
  • Testing: One activity inside QC — the act of executing a system to find defects.
One-liner to rememberQA is process, QC is product, Testing is an activity under QC.

Verification vs Validation

VerificationValidation
"Are we building the product right?""Are we building the right product?"
Static — reviews, walkthroughs, inspectionsDynamic — actually executing the software
Checked against documents/specsChecked against user needs

SDLC — Software Development Life Cycle

The stages a software product goes through from idea to retirement:

  1. Requirement gathering & analysis
  2. Design (HLD/LLD — high/low level design)
  3. Development / Coding
  4. Testing
  5. Deployment
  6. Maintenance

STLC — Software Testing Life Cycle

This sits inside SDLC and is where a QA person actually lives day to day:

  1. Requirement analysis — understanding what needs testing, raising queries on ambiguous requirements
  2. Test planning — deciding scope, tools, timelines, resources; this is where the Test Plan document is written
  3. Test case development — writing test cases and test data
  4. Test environment setup — preparing the environment where tests will run
  5. Test execution — running the test cases, logging bugs
  6. Test cycle closure — reporting metrics, sign-off, lessons learned

Levels of Testing

  • Unit Testing: Smallest piece of code (a function/method), usually done by developers.
  • Integration Testing: Checks how modules work together. Common approaches: Big Bang (all at once), Top-down, Bottom-up.
  • System Testing: The whole application tested end to end, as a black box.
  • Acceptance Testing (UAT): Done by or for the client/business to confirm it's ready for release.

Types of Testing You Must Recognise By Name

TypeWhat it checks
Smoke testingIs the build stable enough to test further? A quick, shallow pass.
Sanity testingNarrow, focused check that a specific bug fix or feature works, after minor changes.
Regression testingConfirms old features still work after new code changes. Automation's favourite target.
RetestingRe-running a failed test case after the bug reported in it is fixed.
Exploratory testingUnscripted, simultaneous learning + test design + execution.
Ad-hoc testingInformal, no plan, no documentation — pure random poking to break things.
Functional testingDoes the feature do what it's supposed to do?
Non-functional testingPerformance, load, security, usability — the "-ilities".
Black-box testingTester has no knowledge of internal code, only inputs/outputs.
White-box testingTester has full visibility of code, tests internal logic/paths.
Grey-box testingPartial knowledge of internals — common in API/security testing.

Test Case vs Test Scenario vs Test Plan vs Test Script

  • Test scenario: A high-level "what to test" — e.g. "Verify login functionality."
  • Test case: The detailed step-by-step version of a scenario, with exact steps, input data, and expected result.
  • Test script: The automated code version of a test case.
  • Test plan: The master document — scope, approach, resources, schedule, risks, entry/exit criteria.

Part 02

Bug / Defect Life Cycle

This gets asked almost every single time, in nearly the same wording: "Walk me through the defect life cycle." Learn the sequence, not just the names.

  1. New — bug is logged for the first time.
  2. Assigned — lead assigns it to a developer.
  3. Open — developer starts working on it.
  4. Fixed — developer believes it's resolved, hands back to QA.
  5. Retest — QA re-tests the fix.
  6. Verified / Closed — if the fix works, bug is closed.
  7. Reopened — if the fix didn't actually work, back to developer.

Side branches you should also know:

  • Duplicate: same bug already logged.
  • Rejected: not a valid bug (working as designed, or tester misunderstood requirement).
  • Deferred: valid, but postponed to a future release.
  • Not Reproducible: developer can't recreate the issue — usually sent back for more details/steps.

Severity vs Priority — the classic trap question

SeverityPriority
How badly the bug damages functionality (technical impact)How urgently it needs to be fixed (business impact)
Decided by the testerDecided by the product owner / project manager
Example: app crashes on a rarely-used screen → High severity, Low priorityExample: wrong company logo on homepage → Low severity, High priority
Interview goldAlways give that logo example or a similar one. It shows you understand severity and priority can move independently of each other — that's the whole point of the question.

Part 03

Automation Testing — The Basics

Why automate at all

  • Regression suites get repeated every release — doing it by hand every time wastes people and time.
  • Automation is faster, consistent, and can run overnight or in CI pipelines unattended.
  • It does not replace manual testing — exploratory, usability, and one-off tests are still manual.

What should NOT be automated

  • Tests that change frequently (unstable UI/requirements)
  • One-time tests
  • Usability and exploratory testing (needs human judgement)
  • Tests with very low ROI (rarely used features)

Automation framework types

FrameworkIdea
Linear / Record-PlaybackSimple recorded scripts, no reusability. Good only for demos.
ModularApplication broken into independent modules/scripts, each tested separately, reused across cases.
Data-DrivenTest logic separated from test data (data usually in Excel/CSV/JSON); same script runs with many data sets.
Keyword-DrivenActions defined as "keywords" (e.g. click, type) in a table understood by non-programmers too.
HybridMix of data-driven + keyword-driven + modular — what most real companies actually use.
BDD (Behaviour Driven Development)Tests written in plain English (Gherkin: Given/When/Then) so business + QA + dev all understand them. Tool: Cucumber.

Automation Pyramid — a favourite whiteboard question

Picture a pyramid with three layers, widest at the bottom:

  • Bottom (most tests): Unit tests — fast, cheap, isolated.
  • Middle: Integration / API tests — fewer, but still fast.
  • Top (fewest tests): UI / End-to-end tests — slow, brittle, expensive, but closest to real user behaviour.
Common mistake candidates makeSaying "we should automate everything through the UI." That's called the Ice-Cream Cone anti-pattern (inverted pyramid) and interviewers specifically listen for whether you know it's a bad practice.

Part 04

Programming Core (Java-flavoured, applies to Python too)

Most automation roles use Java or Python. The concepts below are asked regardless of language — know the idea, and be able to say it in whichever language you're using.

OOP concepts — always asked

  • Encapsulation: Wrapping data (variables) and code (methods) together, hiding internal details using access modifiers (private/public). Think of a capsule medicine — you don't see what's inside.
  • Abstraction: Showing only essential features, hiding complexity. Example: you drive a car using a steering wheel without knowing engine internals.
  • Inheritance: One class acquires properties/methods of another — reused instead of rewritten. In automation: a BasePage class that every page object extends.
  • Polymorphism: Same method name behaving differently — method overloading (same name, different parameters, compile-time) and method overriding (child class redefines a parent method, runtime).

Collections you'll actually use in automation

TypeUse case
List (ArrayList)Ordered, allows duplicates. Storing a list of web elements found by findElements().
Set (HashSet)No duplicates. Useful to check uniqueness, e.g. no duplicate links on a page.
Map (HashMap)Key-value pairs. Storing test data like username → expected result.

Exception handling

try {
    driver.findElement(By.id("submit")).click();
} catch (NoSuchElementException e) {
    System.out.println("Element not found: " + e.getMessage());
} finally {
    System.out.println("This always runs");
}
  • Checked exceptions: checked at compile time (e.g. IOException) — must be handled or declared.
  • Unchecked exceptions: occur at runtime (e.g. NullPointerException, ArrayIndexOutOfBoundsException).

String vs StringBuilder

String is immutable — every modification creates a new object. StringBuilder is mutable, faster for repeated concatenation (used a lot when building dynamic XPaths or log messages).

== vs .equals()

== compares references (memory address) for objects. .equals() compares actual content/value. For Strings, always use .equals() unless you specifically want reference comparison.

Part 05

Selenium WebDriver — The Core Tool

What Selenium actually is

Selenium is not one tool — it's a suite:

  • Selenium WebDriver: the API that talks directly to the browser to automate actions. This is what 90% of interview questions are about.
  • Selenium IDE: browser plugin for record-and-playback, quick prototyping.
  • Selenium Grid: runs tests on multiple machines/browsers in parallel.

How WebDriver actually works (architecture — often asked)

Your test script → JSON Wire Protocol / W3C protocol → Browser Driver (like chromedriver.exe) → Real Browser. Each browser has its own driver executable that WebDriver talks to; the driver translates commands into native browser calls.

Locators — how you find elements on a page

LocatorExample
IDdriver.findElement(By.id("username"))
NameBy.name("email")
Class NameBy.className("btn-primary")
Tag NameBy.tagName("input")
Link TextBy.linkText("Forgot Password")
Partial Link TextBy.partialLinkText("Forgot")
CSS SelectorBy.cssSelector("input#username")
XPathBy.xpath("//input[@id='username']")
Priority order to state in interviewID → Name → CSS Selector → XPath (as last resort, since XPath is slower and can be fragile). Saying this order out loud shows maturity.

XPath — the part that trips people up

  • Absolute XPath: starts from root, /html/body/div/input — breaks easily if page structure changes. Avoid.
  • Relative XPath: starts anywhere with //, e.g. //input[@id='username'] — preferred, more stable.
// Common XPath functions
//input[contains(@id,'user')]
//button[text()='Submit']
//div[@class='card']//h2
//*[@id='login']/following-sibling::button
//label[text()='Email']/parent::div//input

Waits — the #1 real-world topic

  • Implicit Wait: tells driver to wait a set time before throwing "element not found," applies globally for the whole driver session.
  • Explicit Wait: waits for a specific condition on a specific element, using WebDriverWait + ExpectedConditions.
  • Fluent Wait: like explicit wait but you also configure polling frequency and which exceptions to ignore while waiting.
WebDriverWait wait = new WebDriverWait(driver, Duration.ofSeconds(10));
WebElement el = wait.until(
    ExpectedConditions.elementToBeClickable(By.id("submit"))
);
el.click();
Never say this in interview"I mix implicit and explicit wait together." Mixing both is a known anti-pattern — it can cause unpredictable wait times. Say you prefer explicit/fluent waits.

Common exceptions you must recognise

ExceptionWhy it happens
NoSuchElementExceptionLocator didn't match any element on the page
ElementNotInteractableExceptionElement found but not visible/enabled to act on
StaleElementReferenceExceptionElement reference is old — the DOM refreshed/changed since it was located
TimeoutExceptionExplicit wait condition never became true in the given time
NoSuchWindowException / NoSuchFrameExceptionTrying to switch to a window/frame that doesn't exist

Handling multiple windows, frames, alerts

// Switch between browser windows/tabs
String main = driver.getWindowHandle();
for (String handle : driver.getWindowHandles()) {
    driver.switchTo().window(handle);
}
driver.switchTo().window(main);

// Switch into an iframe
driver.switchTo().frame("frameName");
driver.switchTo().defaultContent(); // back out

// Handle a JS alert popup
Alert alert = driver.switchTo().alert();
alert.accept();   // OK
alert.dismiss();  // Cancel

Actions class — mouse and keyboard gestures

Actions actions = new Actions(driver);
actions.moveToElement(menuElement).perform();          // hover
actions.dragAndDrop(source, target).perform();          // drag & drop
actions.keyDown(Keys.CONTROL).click(el).keyUp(Keys.CONTROL).perform(); // ctrl+click

Handling dropdowns

Select dropdown = new Select(driver.findElement(By.id("country")));
dropdown.selectByVisibleText("India");
dropdown.selectByValue("IN");
dropdown.selectByIndex(2);

Part 06

TestNG / JUnit — Test Runners

Selenium only automates the browser — it doesn't organise tests, generate reports, or manage test data by itself. That's what TestNG (or JUnit) is for.

TestNG annotations, in the order they run

@BeforeSuite
  @BeforeTest
    @BeforeClass
      @BeforeMethod
        @Test
      @AfterMethod
    @AfterClass
  @AfterTest
@AfterSuite
  • @BeforeMethod / @AfterMethod: runs before/after every single @Test method.
  • @BeforeClass / @AfterClass: once before/after all tests in that class.
  • @BeforeSuite / @AfterSuite: once for the entire test suite (all classes combined via testng.xml).

Assertions

  • Hard Assert: stops test execution immediately on failure (Assert.assertEquals()).
  • Soft Assert: collects all failures and reports them together at the end, using SoftAssert + assertAll(). Useful when you want to check many fields on a form without stopping at the first failure.
SoftAssert softAssert = new SoftAssert();
softAssert.assertEquals(actualTitle, expectedTitle, "Title mismatch");
softAssert.assertTrue(isLoggedIn, "Login failed");
softAssert.assertAll(); // reports all collected failures

Data Provider — feeding multiple data sets to one test

@DataProvider(name = "loginData")
public Object[][] getData() {
    return new Object[][] {
        {"user1", "pass1"},
        {"user2", "pass2"}
    };
}

@Test(dataProvider = "loginData")
public void loginTest(String username, String password) {
    // this method runs once per row above
}

Other TestNG features worth naming

  • Priority: @Test(priority = 1) controls execution order.
  • Groups: @Test(groups = "smoke") lets you run only a subset of tests.
  • Dependencies: @Test(dependsOnMethods = "login") skips a test if its dependency failed.
  • Parallel execution: configured in testng.xml to run tests/classes/methods in parallel threads.
  • Retry Analyzer: re-runs a failed test automatically to rule out flakiness before marking it a real failure.

Part 07

Framework Design — Page Object Model & Beyond

Page Object Model (POM) — the single most-asked design topic

Instead of writing locators and actions directly inside test methods, you create one class per page of the application. That class holds the page's locators and the actions you can do on it. Tests then just call those methods — readable, and if the UI changes, you fix the locator in one place only.

public class LoginPage {
    WebDriver driver;
    By username = By.id("username");
    By password = By.id("password");
    By loginBtn = By.id("loginBtn");

    public LoginPage(WebDriver driver) {
        this.driver = driver;
    }

    public void login(String user, String pass) {
        driver.findElement(username).sendKeys(user);
        driver.findElement(password).sendKeys(pass);
        driver.findElement(loginBtn).click();
    }
}

// In the test class:
LoginPage loginPage = new LoginPage(driver);
loginPage.login("qa_user1", "Test@123");

PageFactory — POM's helper

An extension of POM using @FindBy annotations instead of manually writing driver.findElement everywhere, plus lazy initialisation of elements (they're located only when actually used).

@FindBy(id = "username")
WebElement usernameField;

public LoginPage(WebDriver driver) {
    this.driver = driver;
    PageFactory.initElements(driver, this);
}

Why frameworks matter beyond POM

  • Reusability: common actions written once, used everywhere.
  • Maintainability: one change point when UI changes.
  • Readability: business-readable test steps, especially with BDD.
  • Reporting: integration with tools like Extent Reports or Allure to show pass/fail with screenshots.

BDD with Cucumber — plain English tests

Feature: Login functionality

  Scenario: Successful login with valid credentials
    Given the user is on the login page
    When the user enters valid username and password
    And clicks the login button
    Then the user should see the dashboard

Each line (Given/When/Then) maps to a Java/Python method behind the scenes called a "step definition." This lets non-technical stakeholders read and even help write test scenarios.

A typical hybrid framework, layer by layer

  1. Config layer: config.properties — URLs, browser choice, environment.
  2. Driver/base layer: setup and teardown of WebDriver, singleton driver management.
  3. Page Objects: one class per screen.
  4. Test data layer: Excel/JSON/CSV feeding data-driven tests.
  5. Utilities: reusable helpers (screenshot capture, wait helpers, Excel readers).
  6. Test/spec layer: actual @Test methods or Cucumber feature files.
  7. Reporting layer: Extent Reports/Allure, plugged in via TestNG listeners.
  8. CI integration: Jenkins/GitHub Actions trigger the suite on every commit.

Postman — the manual API testing tool

  • Send requests, inspect responses, chain requests using variables.
  • Collections: group related requests together.
  • Environments: switch base URLs/tokens between dev, staging, prod.
  • Pre-request scripts & Tests tab: write JavaScript assertions on the response, e.g. pm.response.to.have.status(200).
  • Newman: command-line runner for Postman collections — used to run them in CI pipelines.

REST Assured — API automation in Java

    .header("Content-Type", "application/json")
.when()
    .get("/users/1")
.then()
    .statusCode(200)
    .body("name", equalTo("John Doe"));

Part 09

SQL for Testers — Backend Data Validation

QA doesn't need to be a DBA, but you should be comfortable pulling data to verify what the UI/API claims is actually stored correctly.

-- Basic retrieval
SELECT * FROM users WHERE status = 'active';

-- Count records
SELECT COUNT(*) FROM orders WHERE order_date = '2025-06-20';

-- Join two tables
SELECT u.name, o.order_id
FROM users u
JOIN orders o ON u.user_id = o.user_id
WHERE o.status = 'pending';

-- Group and aggregate
SELECT department, COUNT(*) as emp_count
FROM employees
GROUP BY department
HAVING COUNT(*) > 5;

Types of JOIN

  • INNER JOIN: only matching rows in both tables.
  • LEFT JOIN: all rows from left table, matched rows from right (nulls if no match).
  • RIGHT JOIN: opposite of left join.
  • FULL OUTER JOIN: all rows from both, matched where possible.

WHERE vs HAVING: WHERE filters rows before grouping, HAVING filters groups after GROUP BY is applied.

Primary key vs Foreign key: Primary key uniquely identifies a row in its own table. Foreign key is a column that refers to a primary key in another table, enforcing referential integrity.

Part 10

Git & CI/CD

Git commands used daily

git clone <repo-url>
git checkout -b feature/login-tests
git status
git add .
git commit -m "add login page object and tests"
git push origin feature/login-tests
git pull
git merge main
git log --oneline

Merge vs Rebase: merge creates a new commit joining two histories (preserves full history, can look messy). Rebase moves your commits on top of the target branch (cleaner linear history, rewrites commit hashes).

Merge conflict: happens when the same lines of a file were changed differently in two branches — Git can't decide automatically, so you edit the file manually to resolve it, then commit.

CI/CD — Continuous Integration / Continuous Delivery

  • CI: every code commit is automatically built and tested, catching problems early.
  • CD: the tested build is automatically prepared (Delivery) or even automatically pushed (Deployment) to production-like environments.
  • Where automation fits in: your automated regression suite is triggered as one stage of the pipeline — if tests fail, the pipeline can be configured to block the release.

Common tools you should be able to name: Jenkins (pipeline orchestration, Jenkinsfile), GitHub Actions/GitLab CI (YAML-based pipelines), Docker (consistent environments to run tests in), Maven/Gradle (build and dependency tools for Java projects that also trigger TestNG suites).

Part 11

Agile / Scrum for QA

  • Sprint: a fixed short cycle (usually 1–2 weeks) in which a set of work is planned and delivered.
  • Sprint Planning: team decides what will be done this sprint.
  • Daily Stand-up: quick daily sync — what I did, what I'll do, any blockers.
  • Sprint Review: demo of completed work to stakeholders.
  • Sprint Retrospective: team discusses what went well/badly, to improve the next sprint.
  • User Story: a feature described from the user's perspective — "As a <user>, I want <goal>, so that <benefit>."
  • Acceptance Criteria: the conditions a story must meet to be considered "done" — QA writes test cases directly from these.
  • Definition of Done (DoD): the checklist that must be true for any story to count as complete (coded, tested, reviewed, documented).
Where QA sits in AgileQA isn't a separate phase at the end anymore — testers are involved from sprint planning (writing acceptance criteria, estimating test effort) all the way through to the demo. This "shift-left" mindset is worth mentioning explicitly in interviews.

Part 12

Cypress & Playwright — Modern Alternatives

Interviewers increasingly ask "have you heard of/used Cypress or Playwright?" even for Selenium-heavy roles. You don't need deep expertise, just enough to answer intelligently.

Cypress

  • JavaScript-only, runs directly inside the browser (not through a separate driver like Selenium) — this makes it faster with automatic waiting built in.
  • Great developer experience: time-travel debugging, automatic screenshots/videos on failure.
  • Limitation: historically single-tab, single-browser-origin per test, weaker multi-tab support than Selenium/Playwright.
describe('Login', () => {
  it('logs in with valid credentials', () => {
    cy.visit('/login');
    cy.get('#username').type('qa_user1');
    cy.get('#password').type('Test@123');
    cy.get('#loginBtn').click();
    cy.url().should('include', '/dashboard');
  });
});

Playwright

  • Built by Microsoft, supports Chromium, Firefox, and WebKit with one API.
  • Supports multiple languages (JS/TS, Python, Java, .NET).
  • Auto-waiting, built-in parallelisation, and network request interception out of the box.
  • Generally seen as the fastest-growing modern tool, often compared directly against Selenium in interviews.

Selenium vs Cypress vs Playwright — the comparison question

SeleniumCypressPlaywright
LanguagesJava, Python, C#, JS, Ruby...JavaScript/TypeScript onlyJS/TS, Python, Java, .NET
Cross-browserYes, mature, widest supportLimited (improving)Yes, strong
SpeedSlower (separate driver hop)FastFast
Auto-waitNo, manual waits neededYes, built-inYes, built-in
